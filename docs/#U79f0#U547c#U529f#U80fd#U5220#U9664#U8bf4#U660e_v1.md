# 「称呼」功能删除说明（窗口7后置修复）

## 背景

全局「称呼」（ProfileScreen「AI 配置」区块顶部，默认值"旅人"）此前会真的注入
prompt，与每个角色自己配置的「私下/公开称谓」字段叠加在一起，拼出类似
"旅人是你的老公"这种语义歧义句式——"旅人"读起来像是用户的本名，紧跟在关系
判断词前面，容易被模型误读成一句奇怪的身份宣称，而不是"你和用户之间是配偶
关系"这层单纯的事实陈述。

确认结论：AI 实际怎么称呼用户，完全由角色自己的私下/公开称谓字段和角色自身
语言习惯决定，全局「称呼」从未真正影响这一点。因此本次**完全删除**这个功能
及其 UI 入口，不保留任何兜底或降级形态，prompt 里不再注入任何名字，关系描述
完全交给各角色自己的称谓字段，统一用"用户"这一通用词代替。

## 删除范围

### 整文件删除（2个）
- `data/repository/UserProfileRepository.kt` — 「称呼」的 SharedPreferences 封装
- `ui/screen/ProfileUserCard.kt` — 「编辑称呼」弹窗（`EditNicknameDialog`）

### UI 层
- `ui/screen/ProfileScreen.kt` — 删除 `userName`/`showEditNicknameDialog` 状态、
  `EditNicknameDialog` 调用块、传给 `AiConfigSection` 的 `userName`/`onEditNickname` 参数
- `ui/screen/ProfileAiConfigSection.kt` — 删除函数签名的 `userName`/`onEditNickname`
  参数，及卡片内"称呼"整行 UI（标签、可点击行、chevron 图标、下方分隔线）
- `ui/viewmodel/ProfileViewModel.kt` — 删除 `getUserName()`/`setUserName()`
- `ui/component/CommonDialogs.kt` — 更新头部历史说明注释，标注 `EditNicknameDialog`
  已随本次删除

### 依赖注入 / 调用链（4条真实对话路径）
- `data/AppContainer.kt` — 删除 `userProfileRepo` 单例字段及 import
- `ui/viewmodel/ChatViewModel.kt` — 删除传给 Orchestrator 的 `getUserName` lambda
- `ui/viewmodel/ChatMessageOrchestrator.kt` — 删除构造参数 `getUserName`、
  `buildSystemPrompt` 调用处的 `userName` 传参、未使用的 import
- `ui/viewmodel/RoundtableBotReplyGenerator.kt` — 删除 `buildSystemPrompt` 调用处
  的 `userName` 传参
- `ui/viewmodel/RoundtableIdleManager.kt` — 同上
- `data/agent/AgentTaskJobExecutor.kt` — 删除局部 `UserProfileRepository(context)`
  实例化、import、`buildSystemPrompt` 调用处的 `userName` 传参

### Prompt 语义层（核心修正）
- `data/prompt/PromptOrchestrator.kt`
  - `buildSystemPrompt()` 公开签名删除 `userName: String = "你"` 参数
  - `buildUserIdentityBlock()`：删除 `userName` 参数；`[关于${userName}]` →
    `[关于用户]`；性别陈述句、**关系判断句**（原"旅人是你的老公"的确切来源）
    均改用"用户"
  - `buildDefaultIdentity()`：删除 `userName` 参数，改用"用户"
  - `buildIdentityBlock()`：删除 `userName` 参数，"你对XX的态度"、
    "她对XX的印象"两处改用"用户"
- `domain/AgentRelationEngine.kt`（女儿关系阶段 prompt，独立的第二条注入路径）
  - `buildPromptSnapshot()` 删除 `userName: String = "你"` 参数——**确认这是个
    死参数**：全项目三处真实调用（`RoundtableBotReplyGenerator`/
    `ChatMessageOrchestrator`/`RoundtableIdleManager`）全部只传 `daughterId`，
    从未真正传过 `userName`，恒为默认值
  - `buildStage1Block`/`buildStage2Block`/`buildStage3Block` 三个阶段文案函数
    同步删除 `userName` 参数，全部改用"用户"

## 未改动的部分

- `AgentTaskJobExecutor.execute()` 的 `context: Context` 入参：函数体内不再使用，
  但改变这个签名会影响 Worker 侧调用方，超出本次范围，未动
- 角色自己的私下/公开称谓字段（`userRoleLabelPrivate`/`userRoleLabelPublic`）及
  其圆桌场景切换逻辑：这正是本次修复要保留、且不再被"称呼"干扰的部分，未改动
- 性别注入逻辑（`userGender`/`parseUserGenderType`）：与「称呼」是两个独立字段，
  未改动，只是文案里的代词从 `${userName}` 换成了"用户"

## 自检结果

- 文件数：418 → 416（对应删除的 2 个整文件）
- 全项目扫描确认以下标识符已无代码引用（仅剩历史说明性注释中的字面提及）：
  `userName`、`UserProfileRepository`、`userProfileRepo`、`旅人`、
  `EditNicknameDialog`、`showEditNicknameDialog`、`getUserName`、`setUserName`、
  `onEditNickname`
- 括号平衡自检：修改的 12 个文件中，仅 `ChatMessageOrchestrator.kt` 圆括号计数
  与原始版本一致地存在 3 个差值（304/307 → 302/305，差值不变），确认是文件内
  中文注释夹杂零散英文括号导致，与本次两处编辑无关，非真实语法错误
- `buildSystemPrompt`/`buildPromptSnapshot` 所有真实调用点均使用具名参数或纯
  位置单参数调用，删除中间可选参数不会造成参数错位
